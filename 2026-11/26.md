## 1. 리눅스 링크 (하드 링크 vs 심볼릭 링크)

**한 줄 요약:** 하드 링크는 데이터 자체에 붙은 또 하나의 이름이고, 심볼릭 링크는 원본의 경로를 적어둔 메모다.

### 먼저 알아야 할 것: inode
리눅스에서 파일은 두 부분으로 나뉜다.
- **inode**: 실제 데이터가 어디 있는지, 크기, 권한 등을 담은 본체. 고유 번호가 있다.
- **파일 이름**: 그 inode를 가리키는 이름표일 뿐이다.

### 비교

| | 하드 링크 (`ln`) | 심볼릭 링크 (`ln -s`) |
|---|---|---|
| 가리키는 대상 | 데이터(inode) 자체 | 원본의 **경로(이름)** |
| inode 번호 | 원본과 같음 | 자기만의 inode |
| 원본 내용 수정 | 반영됨 | 반영됨 |
| 원본 이름 변경/삭제 | 계속 열림 | 깨짐 (No such file) |
| 디렉토리 / 다른 파일시스템 | 불가 | 가능 |

### 실습
```bash
$ ln file1 hardlink_file
$ ln -s file1 symlink_file1
$ ls -li
2752631 -rw-rw-r-- 2 user user 0 ... file1
2752631 -rw-rw-r-- 2 user user 0 ... hardlink_file
2753497 lrwxrwxrwx 1 user user 5 ... symlink_file1 -> file1
```
- `file1`과 `hardlink_file`은 **inode 번호가 같다(2752631)**. 같은 데이터를 가리키는 이름 두 개라는 뜻이다.
- 권한 다음 숫자(**링크 수**)가 둘 다 2다. 데이터에 이름표가 2개 붙어 있다는 뜻이다.
- 심볼릭 링크의 크기가 **5바이트**인데, `file1`이라는 경로 글자 수다. 경로만 담고 있다는 증거다.

```bash
$ echo asdf > file1
$ rm file1
$ cat hardlink_file      # asdf  ← 데이터는 그대로
$ cat symlink_file1      # No such file or directory  ← 깨짐
```
`rm`은 데이터를 지우는 게 아니라 **이름표 하나를 떼는 것**이다. 링크 수가 2 → 1로 줄었을 뿐이고, 링크 수가 0이 되어야 데이터가 실제로 지워진다.

```bash
$ echo new > file1
$ cat hardlink_file      # asdf
$ cat symlink_file1      # new
```
같은 이름으로 새 파일을 만들자 깨졌던 심볼릭 링크가 **새 파일**을 따라갔다. 심볼릭 링크는 데이터가 아니라 "file1"이라는 이름만 기억한다는 걸 확인했다.

### 헷갈렸던 점
처음엔 "하드 링크 = 원본의 백업"이라고 생각했다. 하지만 하드 링크는 복사본이 아니라 **같은 데이터에 붙은 이름이 하나 더 있는 것**이다. 그래서 원본 내용을 고치면 하드 링크에도 그대로 보인다. 차이가 나는 건 **이름이 사라졌을 때뿐**이다.

### 보안 관점
심볼릭 링크는 이름만 따라가기 때문에, 공격자가 링크가 가리키는 자리에 다른 파일을 끼워 넣으면 프로그램이 엉뚱한 파일을 읽거나 쓰게 만들 수 있다. 업로드한 압축 파일 안에 `/etc/passwd`를 가리키는 심볼릭 링크를 넣는 공격도 같은 원리다.

## 2. 프로세스

**한 줄 요약:** 프로그램은 디스크에 저장된 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 실행 중인 상태다.

- **PID**: 프로세스마다 붙는 고유 번호. **PPID**는 나를 실행한 부모 프로세스의 번호다.
- **포그라운드 / 백그라운드**: 명령 끝에 `&`를 붙이면 백그라운드에서 실행되고, 터미널을 바로 다시 쓸 수 있다.
- **작업 제어**: `Ctrl+Z`로 일시 정지, `jobs`로 목록 확인, `fg`/`bg`로 앞/뒤로 보내기.
- **kill**: 프로세스를 "죽이는" 명령이 아니라 **시그널을 보내는** 명령이다.
  - `kill PID` → 기본값 SIGTERM(15): 정리하고 종료해 달라는 요청
  - `kill -9 PID` → SIGKILL(9): 즉시 강제 종료 (프로세스가 거부할 수 없음)

```bash
$ ps -ef        # 실행 중인 프로세스 목록
$ sleep 100 &   # 백그라운드 실행
$ jobs
$ kill %1
```

## 3. Web3: 블록체인 기초

### 핵심 개념
- **블록체인**: 해시로 블록을 엮고, 수천 개 노드가 같은 장부를 들고, 합의 규칙으로 다음 블록을 정한다. 중간 블록 하나를 바꾸면 해시가 달라져서 뒤의 블록이 전부 깨진다.
- **합의**: 이더리움은 2022년에 PoW에서 PoS(ETH를 담보로 맡긴 검증자가 블록 생성)로 전환했다.
- **키**: 개인키 → 공개키 → 주소. 반대 방향 계산은 불가능하다. 주소는 공개해도 되지만 개인키와 시드 문구는 절대 공유하면 안 된다.
- **트랜잭션**: from, to, value, data, nonce(계정의 거래 순번), 서명.
- **가스**: 연산량 단위. **수수료 = 사용 가스 × 가스 가격**. 1 ETH = 10⁹ gwei = 10¹⁸ wei.

### 실습: Sepolia 첫 트랜잭션에서 발견한 것
Account 1 → Account 2로 0.01 SepoliaETH를 두 번 보냈다.

| | 1차 송금 | 2차 송금 |
|---|---|---|
| Account 2 상태 | 존재하지 않음 | 이미 존재 |
| 사용 가스 | **204,600** | **21,000** |
| 수수료 | 약 0.000307 ETH | 약 0.0000315 ETH |

단순 송금은 21,000 가스라고 배웠는데, 첫 송금은 약 10배가 나왔다.

**원인:** Sepolia에는 이더리움 다음 업그레이드인 **Glamsterdam**이 먼저 적용되어 있다.
- **EIP-8037**: 새로운 상태(새 계정, 새 저장 슬롯)를 만드는 비용이 올랐다. 존재하지 않는 계정으로 보내면 계정 생성 비용 183,600 가스가 추가된다. → 21,000 + 183,600 = **204,600** ✅
- **EIP-7708**: 모든 ETH 송금이 ERC-20과 같은 `Transfer(address,address,uint256)` 로그를 남긴다. 그래서 순수 ETH 송금인데도 시스템 주소 `0xffff...fffe`에서 로그가 찍혔다.

두 번째 송금에서 가스가 정확히 21,000으로 나오면서 가설이 확인됐다.

**배운 점:** 숫자가 예상과 다르면 공식으로 역산해 보고, 로그와 상세 정보로 증거를 모아 원인을 찾는다. 가스를 하드코딩한 코드는 이런 규칙 변경에서 깨질 수 있다.

## 4. 오늘의 삽질: SSH 키로 서버 접속하기

워게임 서버에 비밀번호 대신 **SSH 개인키**로 접속해야 했다.

```bash
ssh -i key dream@<host> -p <port>
```

### 에러 1: `Load key "key": error in libcrypto`
- **원인:** 키를 터미널에 붙여넣다가 `-----END OPENSSH PRIVATE KEY-----` 줄이 빠지고, 맨 위에 빈 줄이 들어갔다. 키 파일은 시작 줄부터 끝 줄까지 한 글자도 틀리면 안 된다.
- **해결:** 키를 다시 붙여넣고 빈 줄 삭제(`sed -i '/^$/d' key`)
- **확인 방법:** `ssh-keygen -y -f key`로 공개키가 출력되면 정상이다. (개인키 → 공개키 계산은 가능하다는 걸 여기서도 확인)

### 에러 2: `Permissions 0664 for 'key' are too open`
- **원인:** 파일을 새로 만들면서 권한이 `rw-rw-r--`(다른 사용자도 읽기 가능)이 됐다. SSH는 남이 읽을 수 있는 개인키를 노출된 키로 보고 사용을 거부한다.
- **해결:** `chmod 600 key` → `-rw-------` (소유자만 읽기/쓰기)

### 그 외에 배운 것
- 권한이 없다고 무작정 `chmod`부터 할 게 아니라, `id`로 내가 어떤 그룹에 속해 있는지 먼저 확인하자. 권한은 소유자만 바꿀 수 있다.
- 터미널은 받은 글자 중 일부를 "명령"으로 해석한다(줄바꿈, 커서 이동 등). 화면에 보이는 게 전부가 아닐 수 있으니, `cat -A`나 `xxd`로 실제 바이트를 확인하는 습관을 들이자.
